# Варианты технической реализации

Этот документ фиксирует варианты для обсуждения. Финальный стек пока **не выбран**.

## 1. Камера в React Native

### Вариант A — react-native-vision-camera
**Плюсы**
- высокая производительность;
- frame processors позволяют обрабатывать кадры близко к нативному коду;
- хорошо подходит для realtime computer vision;
- активно используется в React Native-проектах.

**Минусы**
- потребуется нативная настройка Android/iOS;
- CV-логику всё равно придётся подключать отдельно.

**Предварительная оценка:** основной кандидат.

### Вариант B — Expo Camera
**Плюсы**
- проще стартовать;
- удобнее, если приложение остаётся максимально Expo-managed.

**Минусы**
- меньше контроля над realtime pipeline;
- сложнее строить тяжёлую обработку каждого кадра.

**Предварительная оценка:** хорош для обычной камеры, слабее подходит для нашего CV-heavy сценария.

## 2. Детекция границ карт

Нужно определить четыре угла каждой карты в кадре независимо от того, знаем ли мы уже, что это за карта.

### Вариант A — OpenCV: contours + quadrilateral detection
Pipeline:
1. grayscale / blur;
2. edge detection;
3. contours;
4. поиск выпуклых четырёхугольников подходящего aspect ratio;
5. perspective transform.

**Плюсы**
- не нужна обученная модель;
- хорошо объяснимо и отлаживаемо;
- для прямоугольных физических карт может работать очень хорошо;
- быстрый MVP.

**Минусы**
- чувствительность к фону, бликам и перекрытиям;
- несколько лежащих вплотную карт могут сливаться;
- потребуется настройка эвристик.

### Вариант B — object detection model (YOLO / MobileNet SSD / аналог)
Обучаем модель находить `card` как объект.

**Плюсы**
- потенциально устойчивее к сложному фону и частичным перекрытиям;
- меньше ручных CV-эвристик после хорошего обучения.

**Минусы**
- нужен размеченный dataset фотографий реальных раскладов;
- сложнее pipeline разработки;
- inference тяжелее;
- модель даст bounding box, а для точной перспективы всё равно желательно определить углы.

**Предварительная оценка:** OpenCV логичнее для первой версии; ML-детектор стоит рассматривать, если классический CV окажется нестабилен.

## 3. Идентификация конкретной карты

После perspective correction у нас есть нормализованное изображение неизвестной карты и 19 эталонов.

### Вариант A — ORB feature matching
Ищем локальные ключевые точки и сравниваем дескрипторы с эталонами.

**Плюсы**
- без обучения;
- быстро запускается;
- устойчив к масштабу/повороту в разумных пределах;
- OpenCV умеет всё необходимое;
- 19 карт — очень маленькая база.

**Минусы**
- может страдать на картах с малоинформативными областями или сильными бликами;
- на тысячах карт простой перебор станет дороже;
- требуется аккуратная система confidence/ratio test.

### Вариант B — perceptual hash (pHash/dHash)
Сравниваем нормализованную карту с эталонами по perceptual hash.

**Плюсы**
- очень просто и быстро;
- практически бесплатный поиск даже по большой базе.

**Минусы**
- требует достаточно хорошо выровненной картинки;
- менее устойчив к бликам, перспективе и частичному закрытию;
- похожие по композиции карты могут путаться.

**Предварительная оценка:** полезен как baseline или дополнительный сигнал, но рискован как единственный метод.

### Вариант C — image embeddings + nearest-neighbour search
Небольшая CNN/vision-модель превращает карту в embedding; выбираем ближайший эталон.

**Плюсы**
- лучше масштабируется до сотен/тысяч карт;
- потенциально устойчивее к шуму и визуальным искажениям;
- поиск по векторам быстрый.

**Минусы**
- нужен подходящий мобильный inference runtime;
- generic embeddings не гарантируют, что почти одинаковые карты будут хорошо различаться;
- возможно понадобится fine-tuning на карточках.

### Вариант D — classifier на конкретный каталог карт
Модель имеет 19 классов, затем сотни/тысячи классов.

**Плюсы**
- простой результат: вероятность для каждой карты;
- можно оптимизировать именно под реальные фотографии карт.

**Минусы**
- добавление новых карт требует переобучения;
- нужен тренировочный dataset с аугментациями/реальными фотографиями;
- неудобно масштабировать каталог динамически.

**Предварительная оценка для прототипа:** сначала ORB; embeddings — главный кандидат на следующую стадию масштабирования.

## 4. Комбинированное распознавание

Вместо одного алгоритма можно использовать каскад:

1. OpenCV находит карту и выпрямляет её;
2. дешёвый pHash отбрасывает большинство невозможных кандидатов;
3. ORB сравнивает только несколько лучших кандидатов;
4. если confidence недостаточен — возвращаем `unknown`.

**Плюсы:** быстро, объяснимо, мало ложных распознаваний.

**Минусы:** pipeline сложнее одного алгоритма и требует настройки порогов.

Для 19 карт этап pHash может быть избыточным, но архитектура пригодится при масштабировании.

## 5. Трекинг между распознаваниями

### Вариант A — распознавать каждую карту на каждом обрабатываемом кадре
**Плюсы:** простая архитектура.

**Минусы:** лишняя нагрузка; результаты могут дрожать.

### Вариант B — detection/recognition редко + visual tracking часто
Например:
- camera preview: 30/60 FPS;
- tracking: ~30 FPS;
- полная детекция/идентификация: 2–5 раз/сек или когда tracking потерян.

Можно использовать optical flow / OpenCV trackers / собственное сопоставление углов.

**Плюсы**
- плавный overlay;
- значительно меньше тяжёлых вычислений.

**Минусы**
- больше состояний в pipeline;
- нужно корректно обнаруживать потерю tracking.

**Предварительная оценка:** предпочтительный вариант после первого working prototype.

## 6. Overlay

### Вариант A — обычные React Native absolute-positioned views
**Плюсы:** просто; удобно обрабатывать tap.

**Минусы:** неудобно рисовать перспективные четырёхугольники и сложные эффекты.

### Вариант B — React Native Skia
**Плюсы**
- быстрый realtime canvas;
- удобно рисовать линии, полигоны, glow и анимации;
- хорошо подходит для AR-подобного overlay.

**Минусы**
- ещё одна зависимость;
- hit testing придётся аккуратно связать с полигонами.

**Предварительная оценка:** RN views достаточно для самого первого MVP; Skia выглядит лучше для итогового overlay.

---

## 7. Нативный CV runtime

### Вариант A — OpenCV в нативном Android/iOS модуле / VisionCamera frame processor plugin
**Плюсы:** максимальная скорость, зрелая библиотека.

**Минусы:** C++/JNI/Objective-C++ integration усложняет проект.

### Вариант B — JS/WASM OpenCV
**Плюсы:** меньше собственного нативного кода.

**Минусы:** realtime camera processing на мобильном устройстве может оказаться заметно хуже по производительности и памяти.

**Предварительная оценка:** для реального приложения стоит ориентироваться на нативный OpenCV pipeline.

## 8. Предлагаемые конфигурации для выбора

### Конфигурация 1 — самый быстрый proof of concept
- React Native
- react-native-vision-camera
- OpenCV
- contour/quadrilateral detection
- perspective correction
- ORB matching
- RN Views overlay

**Сильная сторона:** минимум ML и dataset engineering; можно быстро выяснить, работает ли идея вообще.

**Риск:** CV-эвристики могут плохо переживать сложные реальные условия.

### Конфигурация 2 — CV MVP с более качественным UI
- React Native
- react-native-vision-camera
- OpenCV
- ORB matching
- React Native Skia overlay
- recognition 2–5 FPS + tracking между распознаваниями

**Сильная сторона:** уже близко к нужному пользовательскому ощущению.

**Риск:** больше интеграционной сложности до получения первого результата.

### Конфигурация 3 — ML-first
- React Native
- react-native-vision-camera
- TFLite/ONNX Runtime
- object detector
- image embeddings
- nearest-neighbour retrieval
- Skia overlay

**Сильная сторона:** потенциально лучше масштабируется и устойчивее в реальном мире.

**Риск:** существенно больше работы с dataset и моделями до первого прототипа.
