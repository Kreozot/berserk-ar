# ADR 0002: Кеш Gradle и измерение этапов Android CI

Status: Accepted
Date: 2026-09-22
Area: Technology

## Контекст

Android job в GitHub Actions занимает более 10 минут. npm-кеш уже включён, но Gradle на каждом новом runner повторно скачивает зависимости и пересоздаёт часть промежуточных результатов. Без раздельных замеров неизвестно, сколько времени уходит на установку npm-пакетов, генерацию Android-проекта и собственно сборку.

## Решение

Использовать `gradle/actions/setup-gradle` после `expo prebuild` (Gradle-файлы отсутствуют до генерации Android-проекта) с базовым кешем Gradle User Home и запускать `assembleDebug` с `--build-cache`. Разрешить запись кеша также из PR, чтобы сравнить два прогона до слияния. Сохранять длительность `npm ci`, `expo prebuild` и `assembleDebug` в summary Android job. Не кешировать целиком `node_modules` и генерируемую папку `android/`: они создаются из lockfile и конфигурации Expo, а полный кеш усложнил бы проверку актуальности.

## Последствия

Повторные сборки могут повторно использовать зависимости и кешируемые результаты Gradle. Первый запуск заполняет кеш и не обязан ускориться. Не все задачи нативной сборки кешируемы, поэтому эффект нужно оценить по двум последовательным CI-прогонам и их summary. Если основное время останется в `assembleDebug`, отдельно исследовать дорогие задачи Gradle и применимость более глубокого кеширования.
